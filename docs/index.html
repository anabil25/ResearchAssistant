Research Assistant on Azure

An evidence-governed research accelerator for higher education: researchers work in a Next.js workbench whose API calls seven Foundry Hosted Agents across six studios — Literature, Grant, Matching, Dataset Lab, Screening, and Institutional Q&A — plus a workflow-automation surface, with deterministic approval gates on every write.

How it works

The research API resolves identity, evidence, and approvals, then calls one Hosted specialist per capability. Every public-source call leaves through one governed API Management egress.

There is no agent-to-agent fan-out. The API derives tenant identity, filters Azure AI Search, resolves citations, and records approvals, then invokes exactly one Hosted specialist for the requested capability. research-coordinator is deployed as the workflow-orchestration surface, but graph validation is deterministic Python — it is not a runtime router.

API Management is the only path to the public internet. Nothing else in the solution egresses. It publishes each research source twice — as an MCP server that the single shared Foundry Toolbox (research-shared, immutable versions) binds to, and as a normalized REST API the research API calls with its managed identity. Connector access is derived from saved administrator policy and the assigned specialist; institution-agent has no external tools at all. Per-operation policies validate every parameter, normalize each upstream response, and apply rate limits, and source API keys live only as APIM named values — so no agent, container, or model ever sees a credential.
